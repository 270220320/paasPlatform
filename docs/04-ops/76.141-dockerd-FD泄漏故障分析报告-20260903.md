# 192.168.76.141 dockerd FD 泄漏故障分析报告

| 项 | 内容 |
|---|---|
| 故障主机 | 192.168.76.141（司空私有化部署服务器，Ubuntu，16C/64G） |
| 故障对象 | `dockerd`（PID 1266，Docker Engine 27.2.0，2026-07-01 启动，已运行 63 天） |
| 发现时间 | 2026-09-02 02:06 UTC（初诊）／2026-09-03 07:22 UTC（复诊取证） |
| 报告用途 | 提供给司空私有化团队定位与修复，附全部可复现命令 |
| 影响等级 | 中：业务容器当前全部 healthy、前端/网关正常，但 `docker logs` 已挂起、load 12/16 核，泄漏持续，最终将拖垮 Docker API |

---

## 1. 结论摘要（TL;DR）

1. **确认 dockerd 进程存在持续、恒速的 socket FD 泄漏**：29 小时内从 34,815 涨到 38,323，速率恒定 **约 120 个/小时（每 30 秒 +2）**，无自愈迹象。
2. **泄漏形态已锁定**：`NGoroutines(38,786) ≈ NFd(38,325)`，几乎一比一同步增长 —— 每泄漏 1 个 socket FD 挂着 1 个 goroutine，属于 **Docker API 流式会话（logs/attach/stats/events/exec 流）在 dockerd 服务端未正确关闭** 的典型形态。
3. **37,719 个 socket FD 中 37,706 个是孤儿**：不在内核 `/proc/net/tcp`、`tcp6`、`unix`、`netlink`、`packet` 任何协议表中，即对端早已不存在、连接早已拆除，仅剩 dockerd 单方面持有 FD。
4. **触发方在本机、且全部属于司空私有化服务栈**：dockerd 未监听任何 TCP API 端口（仅 systemd fd:// + `/run/docker.sock`），外部无法直连 Docker API；该宿主机上消费 Docker 流式 API 的客户端（docker-stats-exporter、cadvisor、portainer、97 个容器的 healthcheck exec 等）全部为司空私有化部署自带组件。
5. **责任边界**（客观描述，供参考）：泄漏的载体是 dockerd 27.2.0 的会话清理缺陷（或客户端库未正确断流触发其缺陷）；触发源是司空栈内某组件以 30 秒周期反复建立流式会话。两者共同作用，需双方各自排查。

## 2. 故障现象

| 现象 | 证据 |
|---|---|
| dockerd 高 CPU | 生命周期平均 62.8%（单核），RSS 1.26 GB，349 线程 |
| `docker logs` 挂起 | `docker logs rabbitmq --tail 15` 超过 240 秒无响应 |

## 3. 证据链（附采集命令，均可复现）

### 3.1 FD 数量与泄漏速率

```
# T0 = 2026-09-02 02:06 UTC
ls /proc/1266/fd | wc -l              # 34,815（其中 socket 34,216）
# T1 = 2026-09-03 07:22 UTC
ls /proc/1266/fd | wc -l              # 38,323（其中 socket 37,720）
# 增速 = 3,508 / 29.27h ≈ 120 FD/h ≈ 2 FD/min

# 60 秒精确采样（2026-09-03 07:22→07:23 UTC）
T0: fd=38,323 socket=37,720  NFd=38,325  NGoroutines=38,786
T1: fd=38,325 socket=37,722  NFd=38,327  NGoroutines=38,788   # 60 秒 +2，与均值吻合
```

> 采集命令：
> ```bash
> sudo ls /proc/1266/fd | wc -l
> sudo ls -l /proc/1266/fd | grep -c 'socket:'
> sudo curl -s --unix-socket /var/run/docker.sock http://localhost/info \
>   | grep -oE '"NFd":[0-9]+|"NGoroutines":[0-9]+|"ServerVersion":"[^"]+"'
> ```

### 3.2 关键判决性证据：NFd ≈ NGoroutines 且同步增长

```
docker info（经 unix socket 拉取）：
ServerVersion 27.2.0
NFd         38,325   ←→  NGoroutines 38,786   （差值 ~460，为常驻 goroutine 基数）
Containers  102（Running 97）   Driver overlay2
```

dockerd 内部"一个流式连接一个 goroutine"是 logs/attach/stats(stream)/events/exec 输出流的实现模式。goroutine 与 FD 一比一堆积 ⇒ **存在客户端反复建立流式会话、会话结束后服务端 goroutine 与 socket 未释放**。

### 3.3 孤儿 socket 判定（inode 全量对照内核协议表）

将 dockerd 全部 37,719 个 socket FD 的 inode 与五张内核表逐一比对：

| 内核表 | 命中数 |
|---|---|
| /proc/net/tcp + tcp6 | 0 |
| /proc/net/unix | 13（docker.sock 监听×2、libnetwork、metrics.sock 等正常项） |
| /proc/net/netlink | 0 |
| /proc/net/packet | 0 |
| **孤儿（任何表都无）** | **37,706** |

> 采集脚本（root 执行）：
> ```bash
> sudo python3 - <<'EOF'
> import os,re
> sock=set()
> for fd in os.listdir('/proc/1266/fd'):
>     try: t=os.readlink(f'/proc/1266/fd/{fd}')
>     except: continue
>     m=re.match(r'socket:\[(\d+)\]',t)
>     if m: sock.add(int(m.group(1)))
> def load(p,c):
>     s=set()
>     try: L=open(p).read().splitlines()[1:]
>     except: return s
>     for ln in L:
>         f=ln.split()
>         try: s.add(int(f[c-1]))
>         except: pass
>     return s
> known=load('/proc/net/tcp',10)|load('/proc/net/tcp6',10)|load('/proc/net/unix',7)|load('/proc/net/netlink',8)|load('/proc/net/packet',8)
> print('total',len(sock),'orphan',len(sock-known))
> EOF
> ```

结论：**非活跃连接的 CLOSE_WAIT 堆积**（全机 CLOSE_WAIT 仅 1 条）、**非网络对象泄漏**（`docker network ls` 仅 6 个）。是纯粹的会话级泄漏。

### 3.4 泄漏触发源必然在本机

- dockerd 启动参数 `/usr/bin/dockerd -H fd://`，仅 systemd socket + `/run/docker.sock`，**未监听任何 TCP API 端口**（`ss -tlnp` 无 2375/2376）；
- 因此建立流式会话的客户端只能来自宿主机本机进程/容器；
- 本机消费 Docker API 的常驻组件（均为司空私有化栈自带）：
  | 组件 | 使用方式 | 与 30s 周期的吻合度 |
  |---|---|---|
  | docker-stats-exporter | 周期调用 `GET /containers/{id}/stats`（**流式 API**，stream 模式默认长连接） | 高（典型 30s 采集周期） |
  | cadvisor（--docker_only --housekeeping_interval=10s） | Docker API 轮询 + 事件 | 中 |
  | portainer | agent 周期心跳/事件订阅 | 中（30s） |
  | 97 个容器的 healthcheck exec | 每 interval 由 dockerd 执行 exec（产生 exec 会话流） | 中低（若由此产生，需约 0.5% 概率性泄漏） |
  | dronet-monitor / es310-privatization-devops-be 等 | 自带巡检 | 待查 |

  > 恒定 2 FD/min 的节奏与"单个组件、30 秒周期、每次泄漏 1 条流"高度吻合。

## 4. 建议排查步骤（按成本从低到高）

### 第一步：二分法定位触发组件（无需重启业务，预计 1~2 小时）

每停用一个嫌疑组件，观察 10 分钟 FD 斜率（正常应回落到 0/min）：

```bash
# 监控斜率（另开终端）：
while true; do echo "$(date +%T) $(sudo ls /proc/1266/fd | wc -l)"; sleep 60; done

# 依次单独停用（每次一个，观察 10 分钟，无效则 docker start 恢复）：
sudo docker stop docker-stats-exporter     # 首要嫌疑：流式 stats API
sudo docker stop cadvisor                  # 次要嫌疑
sudo docker stop portainer                 # 次要嫌疑
sudo docker stop dronet-monitor            # 待查
```

若某组件停用后斜率归零 ⇒ 触发源确认。

### 第二步：抓 goroutine 栈定位缺陷函数（需要重启 dockerd，建议与修复同窗口）

dockerd 当前未开 debug，无法直接拉 pprof。处置窗口中可临时开启：

```bash
# 1) 停止前先抓一份现场（若有 gdb）：
sudo gdb -p 1266 -batch -ex 'thread apply all bt 8' > /tmp/dockerd-bt.txt 2>&1
# 2) 之后以 --debug 重启 dockerd，常态巡检期间抓取：
sudo curl -s http://127.0.0.1:<debugport>/debug/pprof/goroutine?debug=1 > /tmp/g.txt
#    在 g.txt 中统计阻塞函数名（如 LogDriver/attach/io.Copy/eventFilter），即可精确到缺陷点
```

### 第三步：版本核对与升级

核对 moby 27.2.0 → 27.5+/28.x 的 changelog 中与下列关键词相关的修复：`attach leak`、`logs goroutine`、`stats stream`、`events subscriber`。27.2.0 发布于 2024-07，距当前主线已有大量流会话清理修复。

### 第四步：同机关联异常（顺带核查，可能独立）

- **RabbitMQ**：`docker stats` 抓到瞬时 110% CPU；`rabbitmqctl list_queues` 两次超时（60s/25s 零输出），管理层近乎无响应；beam.smp 12 天累计 435 CPU 小时。AMQP(5672→宿主 30816) 仍在监听、业务连接 running。建议在其容器内重启观察，并核查队列堆积。
- **56789 端口**：宿主机无监听、traefik 端口映射（80/443/19090/308xx/380xx）与 k3s Service 均无此项。若"route 后台"应由此机暴露，需核对部署变更记录（怀疑某次容器重建时丢了端口映射/entrypoint）。

## 5. 处置方案

### 5.1 应急（现在可做，风险低）

1. 上报并预约维护窗口（泄漏到进程 FD 上限前必须重启 dockerd；按当前速率每日 +2,900，`Max open files` 请以 `cat /proc/1266/limits | grep files` 为准预估耗尽日期）。
2. 窗口前避免任何 `docker logs -f` / `docker events` / `docker stats`（无 stream 参数）长挂操作，防止加剧。

### 5.2 窗口操作（预估业务中断 3~10 分钟）

> 注意：**该机 /etc/docker/daemon.json 不存在，即未配置 live-restore**，重启 dockerd 会导致全部 102 个容器重启。

```bash
# 1) 抓现场（可选，见 4.2）
# 2) 通知业务方，停止进行中的飞行任务/媒体上传
# 3) 重启
sudo systemctl restart docker
# 4) 验证容器全部恢复
sudo docker ps --format '{{.Names}}\t{{.Status}}' | grep -cv 'Up'   # 异常数应为 0
# 5) 验证 FD 回落
sudo ls /proc/1266/fd | wc -l    # 正常应 < 2,000
# 6) 48 小时后复查斜率：若仍 >0，说明触发组件仍在，回到 4.1 二分法
```

### 5.3 长期加固

1. **配置 live-restore**（下次重启 dockerd 不中断业务）：
   ```json
   // /etc/docker/daemon.json
   { "live-restore": true }
   ```
2. 监控告警：`dockerd FD > 5,000` 或 `NGoroutines > 10,000` 告警（node_exporter/docker_exporter 可覆盖）。
3. 降低 exec 型 healthcheck 频次、有条件改 HTTP 探针；docker-stats-exporter 加超时与非 stream 模式（`?stream=false`）。
4. 升级 Docker Engine 至 27.5+ / 28.x。
